> 面向已有成熟研效平台的大型组织，探讨 AI 原生（AI-Native）转型下研发流程与协作领域的划分方式，给出可用于分析聚焦与演进规划的问题拆解框架。

## 摘要（TL;DR）

传统研效平台以"大环节"（需求—方案—开发—测试—评审—上线）为骨架划分领域，这一划分建立在两个隐含假设上：**人是所有环节的执行者，平台是为人提效的工具集**。AI 原生实践正在同时击穿这两个假设，由此带来三个结构性判断：

- **判断一：流程维度上，"大循环/小循环"的边界被重画。** 小循环（编码—验证）扩大内卷，把测试、自评审甚至修复都吸入 Agent 自循环；在人与 Agent 之间新生出一个"中循环"（委派—执行—验收的监督循环）；大循环本身没有消失，但瓶颈从"生产代码的速度"整体下移到"验证、评审与消化代码的能力"。对 10 万+ GitHub 开发者的研究显示，自治 Agent 让编码活动提升 **+180%**，但传导到项目交付只剩 **+50%**、到正式发布只剩 **+30%** [^145^]。
- **判断二：协作维度上，问题重心完成"三级跳"——从工具问题，到人的协作问题，再到"人+Agent 混合劳动力"的协作与治理问题。** 协作关系呈现四个层次：人—Agent 结对、人—多 Agent 编排、Agent—Agent 协作、多人—多 Agent 组织，每一层都有独立的问题集（信任校准、上下文工程、协议与身份、责任归属）。
- **判断三：平台维度上，研效平台的服务对象从"人"扩展为"人和 Agent"，平台定位从 IDP（内部开发者平台）升级为混合劳动力的控制平面（Control Plane）。** Gartner 2026 年平台工程 Hype Cycle 已将 Agent 体验（AX）与 AI 原生开发列为核心议题 [^6^]。

据此，本报告建议的问题拆解主框架是一张 **"流程阶段 × 协作层次"问题域矩阵**（7 个流程阶段 × 4 个协作层次），辅以三条分析轴：**循环尺度轴**（小/中/大循环）、**成熟度轴**（L1 工具增强 → L4 自治治理）、**度量轴**（北极星指标 + 护栏指标）。当前行业水位大致处于 **L2 流程融合期向 L3 编排代理期过渡**的阶段（信通院调查中 L3 核心智能化企业占比 29.75%）[^117^]，平台工作的重心应依次落在：平台能力 MCP 化、上下文与知识供给、Agent 注册与编排、证据链与风险分级门禁、以及度量体系重建。

## 一、范式判断：为什么"环节视角"的划分正在失效

### 1.1 三个正在发生的结构性变化

研发效能领域过去十年的主流范式，是把软件交付拆解为一系列边界清晰的大环节，每个环节配备相应的工具链，再用流水线把环节串起来；平台的价值在于缩短环节周期、减少环节间的交接损耗。这一范式在 2024—2026 年间遭遇三股结构性力量的冲击。其一是**执行者身份的变化**：编码 Agent 从"补全工具"进化为可以异步承接完整任务的"准同事"，GitHub Copilot 的云端编码 Agent 可以直接承接 Issue、在云端沙箱中完成开发并提交草稿 PR，人只在 PR 评论中提出修改意见[^68^][^77^]。其二是**流程颗粒度的变化**：当 Agent 可以在分钟级完成"生成—运行—测试—修复"的完整闭环时，原本以天和周为单位设计的阶段门（Stage Gate）就失去了原有的节拍意义，业界开始讨论"Agentic SDLC"对经典生命周期的整体重构[^2^][^4^]。其三是**组织形态的变化**：Gartner 预测到 2028 年 90% 的企业软件工程师将使用 AI 代码助手，开发者角色从"实现者"转向"编排者"[^102^]，团队随之出现"小团队大产出"的 tiny team 形态[^13^]。

这三股力量共同指向一个结论：**领域划分的坐标系需要更换**。继续按"需求平台、CI 平台、测试平台、发布平台"的环节视角切分问题，会系统性地遗漏三类新问题——跨环节的 Agent 自循环问题、人机之间的委派与验收问题、以及 Agent 作为新角色的身份与治理问题。它们恰恰落在传统环节划分的缝隙里。

### 1.2 数据侧写：渗透、增益与"放大器"结论

从渗透率看，头部组织已经越过了"试点"阶段。腾讯 2025 年研发大数据报告显示，超过 90% 的工程师使用 CodeBuddy，**新增代码的 50% 由 AI 生成**，代码评审环节 AI 参与度达 94%，28% 的缺陷由 AI 发现[^70^]；字节跳动内部 AI 编程工具使用率在 2025 年 6 月已超 80%[^58^]，到 2025 年 12 月达到 92% 以上，抖音生活服务团队的 AI 代码贡献占比达 43%[^55^][^43^]；用友集团基于通义灵码的 AI 生成代码占比 37%[^74^]，谷歌超过 30%、微软在 20—30% 区间（均为公司 CEO 公开披露口径）[^150^]。信通院《AI4SE 行业现状调查报告（2026）》显示，29.75% 的企业已进入 L3"核心智能化"阶段（同比增长 68.84%），全国企业 AI 代码平均采纳率 42.61%（同比提升 55%）[^117^]。可以说，**"每个环节都有 Agent"在头部组织已经不是设想而是默认状态**。

![头部组织 AI 生成代码占比](/images/fig4_industry.png)

但效率结论远比渗透率复杂。DORA 2025 年度报告的核心论断是：**AI 是一个放大器（Amplifier）——它放大的是组织原有的工程能力与管理水平，而非凭空创造价值**；AI 提升了交付吞吐，但交付不稳定性的问题依旧存在，且约 90% 的组织已建立内部平台，平台质量成为 AI 价值兑现的前置条件[^36^][^39^]。DX 的研究同样发现了"AI 生产力悖论"：开发者自报每周节省 3 小时 45 分，但组织级真实提升只有 5—15%，PR 数量增长 98% 的同时评审时间增长 91%、代码 churn 率从 3.1% 升至 5.7%[^33^][^34^]。METR 的随机对照实验甚至发现资深开源开发者在 AI 辅助下变慢了 19%，而他们自我感觉变快了 20%[^65^]。这些证据共同说明：**按环节统计的"局部提效"已经无法解释系统级的效能变化**，这正是需要重新做问题拆解的直接动因。

## 二、流程维度：大循环、小循环如何被重构

### 2.1 传统研效平台的"大环节"假设

要讨论循环的变化，先要明确传统划分背后的循环结构。经典研发流程中实际上嵌套着两级反馈循环：**小循环**是开发者本地的"编辑—构建—调试"循环，以秒到分钟计，发生在 IDE 与本地环境之内，几乎不被平台观测；**大循环**是"需求—开发—测试—评审—发布—运营反馈"的业务交付循环，以周到月计，是研效平台的主要管理对象。平台对大循环的管理方式是阶段门：每个环节有明确的准入准出标准（DoR/DoD），环节之间通过工单、流水线、评审单等结构化载体交接，质量保障依赖"越靠后的环节越严格"的人审机制——尤其是代码评审（CR）和上线审批这两个人工闸门。

这一结构成立的前提，是**小循环足够便宜、大循环足够可控**：开发者在小循环里反复试错的成本很低，而大循环每个环节都由人执行，速度天然受限，阶段门的审查强度与环节流速是匹配的。当 Agent 同时改变小循环的成本结构和大循环的流速时，这个匹配关系就被打破了。

### 2.2 小循环内卷：开发—验证—评审被吸入 Agent 自循环

AI 原生开发中最显著的变化，是小循环的"内卷化"——它的半径在扩大、转速在加快、内涵在增厚。DZone 的观察非常精准：**内循环正在吞噬外循环（The Inner Loop Is Eating The Outer Loop）**。编码 Agent 在沙箱中工作时，会在 PR 产生之前就完成数十次"生成—在真实依赖环境中验证—自我评审—修复"的迭代；过去属于外循环专属职能的验证与评审，被大量吸收进 Agent 的工作流，PR 越来越像一份"过程记录"而不是质量闸门，CI 则退化为轻量的持续反馈层[^87^]。GitHub 云端 Agent 的工作方式印证了这一结构：Agent 在隔离环境中自主完成开发和自验证，直到自评通过才提交草稿 PR 请人过目[^68^]。

这一变化的直接后果是**验证能力取代生成能力成为小循环的新通货**。当代码供给近乎无限时，决定小循环转速的不再是"写得多快"，而是"验证得多快、多可信"：沙箱环境能否按需秒级供给真实依赖、测试是否足够完备到可以作为 Agent 的验收信号、静态检查与安全扫描能否嵌入 Agent 的自评回路。SWE-chat 对真实用户会话的研究给出了警示性数据：完全依赖 Agent 的 vibe coding 模式下，代码引入漏洞的速率约为纯人工编写的 **9 倍**、人机协作模式的 5 倍；而人机协作（collaborative）模式反而是单位代码成本最低的模式[^120^]。这说明小循环的健康度不取决于"放手程度"，而取决于**验证回路的工程质量**。

### 2.3 中循环诞生：从"做"到"委派与验收"的监督循环

在小循环（Agent 自转，秒—分钟）和大循环（业务交付，周—月）之间，AI 原生流程新生出了一个过去不存在的循环层：**人—Agent 监督循环**，量级为小时到天。Thoughtworks 将其称为"监督工程"（supervisory engineering）的中循环：工程师的工作从亲手实现，转变为设定意图与约束、把任务委派给 Agent、评审其产出、给予反馈并决定是否合并[^112^]。Anthropic 对数百万次真实人机交互的测量为这个中循环画出了行为曲线：随着经验增长，用户对 Agent 全自动批准的会话占比从约 20% 升至 40% 以上，同时打断与驳回并没有消失——他们逐渐从"逐动作审查"转向"放手执行、按需干预"[^143^]；Claude Code 最长会话的自主工作时长在三个月内从不足 25 分钟翻倍到 45 分钟以上[^143^]。

中循环是问题密度最高的新领域，因为它涉及一整套过去平台从未管理过的交互协议：**任务如何被描述成可委派的规格（Spec）、Agent 的产出如何携带可机器验证的证据、人如何在不被海量 PR 淹没的前提下保持有效验收**。针对一家推行"PR 翻倍"强制令的中型企业的纵向研究（802 名开发者、19.6 万个 PR）揭示了中循环失灵的典型图景：人均吞吐最终达到基线的 2.09 倍，但每位评审者的负荷大致翻倍，自动化评审超过了人工评审，实质性人工评审覆盖率从 48% 跌至 21%，组织实际上是在"绕过评审"消化增量[^79^]。这个案例对所有大型组织都是一个预警：**如果平台只解决"委派"不解决"验收"，中循环会成为质量债务的放大器**。

### 2.4 大循环瘦身与瓶颈下移：从生产速度到消化能力

小循环内卷与中循环成型的合力，使大循环呈现"瘦身"与"升格"并存的形态。瘦身的一面：环节间的交接损耗在下降——需求可以被结构化为机器可执行的规格，开发、测试、评审在小循环和中循环内被高度压缩，阿里云效通过 MCP Server 让 AI 直接读取工作项、编写代码、创建 MR 并触发流水线，把需求到交付串成了一条由 Agent 驱动的闭环[^61^][^52^]。升格的一面：**保留下来的少数人工闸门变得更重要而不是更不重要**——ADLC（Agentic Development Life Cycle）框架把经典 SDLC 的审批门压缩为按风险分级的 HITL（人在环）介入点，低风险变更自动通过、高风险变更强化审查[^4^]；Master of Code 的 AI 原生 SDLC 实践同样以 5 个风险门替代传统的阶段评审[^9^]。

瓶颈下移是这一维度最重要的规律。NBER 工作论文（Demirer 等，覆盖 10 万+ GitHub 开发者的匹配事件研究）用"弱链假说"解释了这一现象：自动补全、交互式 Agent、自治 Agent 分别把编码活动（commits）提升 40%、140%、180%，但这些任务级增益沿生产链急剧衰减——到项目数只剩 50%，到实际发布只剩 30%，AI 与人工投入之间的替代弹性估计仅 0.25，呈现强互补关系[^145^]。Perplexity 产品数据的研究从另一个角度印证了同一方向：当 Agent 承担了任务分解与执行后，用户的后续提问显著向"验证与扩展"等高阶工作迁移[^119^]。**换言之，大循环的约束从"供给端的生产能力"转移到了"消化端的验证、集成与决策能力"**——这正是研效平台在 AI 原生时代最需要重新瞄准的靶心。

### 2.5 七个流程阶段的逐项变化对照

将上述循环视角落到用户提出的具体阶段划分上，可以逐项对照传统平台关注点在 AI 原生条件下的位移。需要强调的是，**阶段本身没有消失，消失的是阶段之间"人搬着工件走路"的交接方式**；每个阶段的核心问题都从"如何让人做得更快"变成"如何让 Agent 做得可信、让人验得过来"。

| 流程阶段 | 传统平台关注 | AI 原生下的核心变化 | 新生产物 / 新问题 |
|---|---|---|---|
| 需求分析 | 需求管理、优先级、流转效率 | 需求被结构化为机器可执行的规格与验收标准（SDD 规约驱动开发兴起[^45^]）；27% 的任务是"没有 AI 就不会去做"的新工作[^141^] | 意图规格化质量；需求→任务的自动分解；验收标准的机器可判定性 |
| 技术方案 | 方案评审、架构决策记录 | 方案库与模式沉淀为 Agent 可检索的知识；架构决策成为少数保留给人的高阶判断[^103^] | 方案的模式化与知识化；跨团队架构一致性治理 |
| 开发实现 | IDE 提效、代码托管、环境 | 上下文工程（AGENTS.md 成为跨工具事实标准[^128^]）；沙箱环境与依赖供给成为 Agent 工作台 | 上下文资产的版本化；多 Agent 并行开发的冲突合并 |
| 开发测试 | 用例管理、自动化率 | 测试成为 Agent 的"验收信号"；测试生成与测试 Agent 上岗，验证环境按需供给[^87^] | 测试完备度决定 Agent 自治上限；测试/开发 Agent 相互对赌机制 |
| 代码评审 | 评审效率、评审质量 | 评审从"逐行人审"转向"机器预检 + 证据链 + 人抽验"；评审负荷向人集中[^79^] | 证据链 PR（产物携带验证证据）；评审 Agent 可信度校准；合并责任归属 |
| 发布上线 | 流水线、审批、灰度 | 变更频率激增冲击流水线承载；审批门按风险分级，低风险自动化、高风险强化[^4^] | 风险分级模型；自动回滚决策边界；全程可审计追溯 |
| 运营运维 | 监控告警、故障响应 | 告警摘要与故障定界由 Agent 完成；自愈在明确权限边界内运行 | 自愈动作权限边界；Token 成本治理（FinOps）[^114^] |

## 三、协作维度：从工具问题、人的协作到混合劳动力协作

### 3.1 协作关系的四次跃迁

用户提出的第二个划分角度——从解决工具问题，到解决人的协作问题，再到人与 Agent、多人与多 Agent 的协作问题——准确刻画了协作重心的迁移路径。将其细化，可以识别出**四次跃迁**：第一次是"人—工具"，平台解决的是效率问题（工具好不好用）；第二次是"人—人"，平台解决的是协作问题（多角色如何围绕流程协同，这是传统研效平台的成熟区）；第三次是"人—Agent"，解决的是**委派与信任问题**；第四次是"多人—多 Agent"，解决的是**组织级的编排与治理问题**。Anthropic《2026 智能体编码趋势报告》把同样的趋势列为头两条：软件开发生命周期正在剧变，且单 Agent 正在进化为协同工作的 Agent 团队[^135^]。

这一跃迁序列的实践含义在于：**四次跃迁不是替代关系而是叠加关系**。工具问题没有消失（Agent 本身也要用工具，且更需要稳定可靠的工具接口——这正是 MCP 协议解决的问题[^20^]），人的协作也没有消失（它转移到了规格对齐、验收决策与责任界定上），但平台的问题清单确实被重写了。下面分三个层次展开。

### 3.2 人—Agent 结对：委派、信任校准与监督谱系

人—Agent 结对是当前渗透率最高、也最先遇到瓶颈的协作层。其核心问题可以归纳为三个。**其一是委派能力**：自然语言任务是模糊规格的载体，把任务描述成"Agent 可执行、结果可判定"的规格，正在成为工程师的核心技能——Anthropic 报告显示开发者约 60% 的工作有 AI 参与，但完全委派的只有 0—20%，委派比例低的原因不是模型能力，而是任务规格化与结果验证的成本[^135^]。**其二是信任校准**：用户对 Agent 的授权随经验增长（自动批准率 20%→40%+），但 Anthropic 同时发现用户对权限弹窗的批准率高达 93%——"审批疲劳"使交互式确认在行为上不可靠，安全不能依赖人的警觉性，而要依靠边界化的自治空间与多层防线[^148^][^143^]。**其三是监督模式的选择**：业界已形成一个从 HITL（人在环中）到 HOTL（人在环上）再到完全自治的监督谱系，升级需要明确的准入条件（如 95% 以上的任务批准率、低于 1% 的错误率、30 天稳定期等）[^80^]。

可以把这一谱系整理为五级自治模型，作为人—Agent 协作层的问题定位标尺：

| 级别 | 模式 | 人的角色 | 适用场景 | 关键平台机制 |
|---|---|---|---|---|
| L0 | 手动 | 操作者（Operator） | 高危变更、未验证领域 | 无 Agent 介入 |
| L1 | 辅助建议 | 咨询者（Consultant）：Agent 建议，人执行 | 陌生代码库、合规敏感模块 | 建议留痕、采纳统计 |
| L2 | 结对协作 | 协作者（Collaborator）：人实时监督每个动作 | 常规功能开发 | 动作级权限、即时回滚 |
| L3 | 委派验收 | 批准者（Approver）：Agent 自主执行，人验收结果 | 边界清晰的任务（迁移、修 bug、补测试） | 任务规格、证据链 PR、草稿合并 |
| L4 | 监督例外 | 观察者（Observer）：Agent 自治，人只看异常与指标 | 低风险批量任务、夜间批处理 | 风险分级、异常升级、全程审计 |

Anthropic 的测量数据显示，当前多数 Claude Code 用户实际运行在 L2—L3 之间[^143^]，这也是平台在人—Agent 层应优先做深的区间：把"委派—执行—验收"的体验与证据链打磨好，比追求 L4 的演示效果更有实际价值。

### 3.3 人—多 Agent 编排与 Agent—Agent 协议

当一名工程师同时驱动多个 Agent（前端、后端、测试、文档各一个），以及当 Agent 之间需要互相调用时，协作问题进入了协议层。2025—2026 年这一层的基础设施快速收敛为一个三层结构：**MCP 解决 Agent 与工具/数据的连接，A2A（Agent-to-Agent）解决 Agent 与 Agent 之间的任务委托与协作，编排框架（如 LangGraph 等）解决流程逻辑与状态管理**[^20^]。A2A 协议的关键设计——Agent Card（能力名片）、带生命周期的 Task、产物（Artifact）——本质上是为 Agent 间的"分工契约"定义了标准格式[^18^]。生态层面的信号也很强：MCP 已被捐赠给 Linux 基金会的 Agentic AI Foundation，微软 Copilot Studio 的多 Agent 编排与 A2A 支持在 2026 年 4 月正式商用[^20^]。

对研效平台而言，这一层的新问题主要有四类。**任务分解与路由**：谁来把需求拆成适合不同 Agent 的子任务（人拆、规划 Agent 拆、还是混合），以及如何评估分解质量。**上下文与记忆共享**：多个 Agent 如何共享同一份项目知识与决策历史而不互相污染，生产级检查清单包括循环检测、状态模式、幂等性与 Token 预算[^20^]。**身份与权限**：每个 Agent 需要独立的身份、最小权限与可吊销凭证，跨 Agent 调用需要网关级的认证授权、审计与成本管控[^18^]。**并行冲突**：多个 Agent 同时改同一仓库时的分支策略与冲突仲裁。值得注意的是，**Agent—Agent 协作在当前阶段的变革压力评分反而低于人—Agent 层**（见第五章矩阵），因为它的前提是先把单个 Agent 的供给、规格与验收做扎实——这与 Anthropic 将"单 Agent 进化为协同团队"列为第二趋势而非第一趋势的判断一致[^135^]。

### 3.4 多人—多 Agent 组织：小团队、全栈专家与角色重构

协作的最高层是组织形态的变化。当个体的产能杠杆被 Agent 放大 5—10 倍后，"多少人配多少 Agent 做什么事"成为新的组织设计问题。行业讨论中浮现出三个方向。**其一是 tiny teams（小团队）**：Gartner 预测工程团队将向小型化演进，少量工程师借助 Agent 完成过去大团队的工作，管理者的关注从"产出量"转向"创造力与影响力"指标[^13^]。**其二是 expert generalist（专家型通才）**：Thoughtworks 观察到 AI 时代的稀缺能力是"既有深度判断又能跨域工作"的通才，因为 Agent 可以补齐具体技能，人需要提供的是品味、判断与系统思维[^103^]。**其三是角色光谱的整体右移**：开发者从实现者转向编排者与验收者[^102^][^105^]，而测试、SRE、技术写作等角色则在向"质量策略师"与"Agent 训练师"演化[^103^]。

多人—多 Agent 层的问题带有强烈的治理属性：**代码所有权与风格一致性**（Agent 大量产出代码后，"谁对这段代码负责"变得模糊）；**知识资产的归属与流转**（Agent 沉淀的上下文、技能包属于个人、团队还是平台）；**责任与问责**（自动化评审超过人工评审后，合并责任如何界定[^79^]）；以及**新人培养断层**（当初级任务都被 Agent 完成，资深工程师从哪里来）。这些问题单个团队无法独立回答，恰恰是平台与工程管理者需要共同设计的部分——这也解释了为什么 DORA 把"明确的 AI 使用立场（clear AI stance）"列为放大 AI 正向效应的七项组织能力之首[^39^]。

## 四、平台维度：研效平台从 IDP 到混合劳动力控制平面

### 4.1 服务对象之变：DX 之外新增 AX

传统内部开发者平台（IDP）优化的对象是开发者体验（DX）。当 Agent 成为平台的第二类用户，平台必须同时优化 **Agent 体验（AX）**——Gartner 2026 年平台工程 Hype Cycle 已把 AX、AI 原生开发与"Agentic AI 的 FinOps"列为最受关注的主题[^6^]。两种体验的诉求截然不同：人需要图形界面、信息架构与低摩擦流程；Agent 需要**结构化的接口（MCP 化的平台能力）、可检索的上下文、确定性的工具语义与机器可判定的反馈信号**。一个形象的判断标准是：如果 Agent 无法像新员工一样"自助入职"你的平台（发现能力、理解语义、获得授权、完成任务），那么平台就还只是为人设计的。

国内外头部平台的动作印证了这一转向。阿里云效把项目管理、代码、流水线等核心能力封装为 MCP Server，使任意兼容 MCP 的 Agent 都能操作研发全流程[^61^]；腾讯 WeDev 研效平台日均支撑 8000 万次以上的数据交换，AnyDev 把环境准备从 1 天压缩到 1 分钟——本质都是在为 Agent 铺路[^70^]；工商银行则明确提出从"编码质效提升"到"研发全流程赋能"再到"AI 主导智能研发"的三步走，已建成 27 项智能研发能力、覆盖 7000 余名开发者，单位时间有效代码量提升 22.9%[^116^]。

### 4.2 控制平面能力清单

当平台同时服务人和 Agent，它就自然演变为"混合劳动力的控制平面"。IBM 将 Agent 控制平面定义为对 Agent 的访问控制、注册、执行管理、生命周期、策略、路由与状态管理的统一治理层[^90^]；2026 年上半年，AWS 推出 Bedrock Agent Registry 集中治理 Agent 身份与能力[^93^]，微软 Agent 365 正式商用、把 Agent 纳入与企业员工相同的身份与合规体系[^96^]。这一市场爆发的背景是治理缺位的风险：Gartner 估计到 2025 年底将有 40% 以上的企业 AI Agent 部署在中央 IT 治理之外[^93^]，42% 的公司曾在 AI 项目投产前放弃[^96^]。

面向研发域的控制平面，能力清单可以归纳为八项：

| 能力域 | 说明 | 代表实践 |
|---|---|---|
| Agent 注册中心 | Agent 的目录、能力名片、版本与归属管理 | AWS Agent Registry[^93^]、GitHub 自定义 Agent（.github/agents）[^77^] |
| 身份与权限 | Agent 独立身份、最小权限、凭证签发与吊销 | 微软 Agent 365 集成 Entra[^96^] |
| 工具网关（MCP Gateway） | 平台能力的 MCP 化发布、认证授权、限流与审计 | 云效 MCP Server[^61^] |
| 策略与风险分级 | 按任务风险决定自治级别与人工介入点 | ADLC 风险门[^4^]、HITL/HOTL 升级条件[^80^] |
| 上下文与知识供给 | 代码库、文档、决策历史的 Agent 可读化（RAG/索引） | AGENTS.md 标准[^128^] |
| 执行沙箱 | 按需供给、带真实依赖、用完即毁的验证环境 | Copilot 云端 Agent 沙箱[^68^]、腾讯 AnyDev[^70^] |
| 可观测与评测 | Agent 行为追踪、任务级评测集、质量回归 | DORA AI 能力模型中的评测与数据生态[^39^] |
| 成本治理 | Token 计量、预算与单位经济核算 | Gartner：2028 年 AI 编码成本或超开发者薪酬[^114^] |

### 4.3 上下文工程：平台的新基础设施工位

在八项能力中，上下文工程值得单独强调，因为它是当前投入产出比最高的平台工作。"Harness Engineering"研究对 2853 个 GitHub 仓库的系统分析发现：仓库级上下文文件（Context Files）是配置编码 Agent 的最主流机制，AGENTS.md 已经演进为跨 Claude Code、Copilot、Cursor、Gemini、Codex 等主流工具的互操作标准，而更高级的机制（技能包、子代理）采用率仍然很低[^128^]。这意味着平台可以沿着一条清晰的梯度推进上下文供给：**先做全组织仓库的 AGENTS.md 覆盖与质量运营（把架构约定、构建命令、测试入口、提交规范写成 Agent 可读的"入职文档"），再做领域知识（需求、方案、故障复盘）的 Agent 可读化，最后把优质工作流沉淀为可复用的技能包（Skills）**。

上下文工程之所以是平台工位而非个人工位，原因在于规模化的质量与一致性：单个团队写的 AGENTS.md 质量参差，平台可以通过模板、静态检查（lint）、效果评测（同一基准任务在不同上下文配置下的成功率）和最佳实践分发，把"上下文质量"变成可度量、可运营的平台指标。DORA 2025 的七项 AI 能力中，"健康的内部数据生态"与"AI 可访问的内部数据"两项都指向同一结论：**数据与上下文的质量，决定 AI 在组织内的放大系数**[^39^]。

## 五、问题拆解框架：一张矩阵 + 三条辅助轴

### 5.1 主框架：流程阶段 × 协作层次问题域矩阵

综合第二、三章的两个维度，可以得到用于日常分析聚焦的主框架：**纵向是 7 个流程阶段（需求分析、技术方案、开发实现、开发测试、代码评审、发布上线、运营运维），横向是 4 个协作层次（人—Agent 结对、人—多 Agent 编排、Agent—Agent 协作、多人—多 Agent 组织）**，交叉而成的 28 个格子即问题域的最小分析单元。每个格子可以用"变革压力/问题密度"打分（1—5），并标注该格的核心问题，用于横向对齐认知、纵向追踪演进。

![AI 原生研发问题域矩阵](/images/fig2_matrix.png)

矩阵揭示了三个结构性热点，应成为演进规划的一号位问题。**热点一在"开发实现 × 人—Agent 结对"（压力值 5）**：上下文工程与 AGENTS.md 体系，是当前一切 Agent 能力的地基[^128^]。**热点二在"代码评审 × 人—Agent 结对"（压力值 5）**：评审负荷向人集中是中循环失灵的震中，2.09 倍吞吐背后是评审覆盖率腰斩[^79^]，证据链 PR 与机器预检是必选项。**热点三在"多人—多 Agent 组织"整列（压力值 3—4）**：责任归属、质量门禁重设、Token 成本与审计，是大型组织区别于小团队的关键战场。相对而言，"Agent—Agent 协作"整列压力适中——不是不重要，而是它的解法依赖前两个热点先打牢。

### 5.2 辅助轴一：循环尺度（时间/反馈半径）

矩阵回答"问题在哪"，循环轴回答"问题按什么节拍演进"。三级循环各有独立的健康度指标：**小循环看验证回路的工程质量**（环境供给时长、测试作为验收信号的可信度、Agent 自评通过率）；**中循环看委派与验收的吞吐质量**（委派任务占比、验收一次通过率、人均评审负荷）；**大循环看端到端交付与消化能力**（变更前置时间、发布频率与失败率、需求到上线的价值周期）。三者之间存在明确的传导关系：小循环的问题会放大为中循环的验收噪音，中循环的拥堵会抵消小循环的全部提速——这正是 +180% 衰减到 +30% 的微观机制[^145^]。

![AI 原生研发流程的三级循环模型](/images/fig1_loops.png)

循环轴对规划的直接启示是：**演进的顺序应当是"先固小循环，再通中循环，后优大循环"**。很多组织的自然冲动是先在大循环上做文章（因为那是管理层看得见的指标），但在验证与验收能力缺位时提速大循环，等于把质量债务以更高利率滚到线上。

### 5.3 辅助轴二：成熟度（L1—L4）

成熟度轴回答"我们在哪、下一步去哪"。综合信通院 AI4SE 成熟度分级[^117^]、Port 的 Agentic SDLC 三阶段（手动 → AI 辅助 → AI 主导）[^2^]与国内银行的"三步走"实践[^116^]，可以把研效平台的 AI 原生演进划分为四级：

![研效平台 AI 原生演进的四级成熟度阶梯](/images/fig3_maturity.png)

| 级别 | 阶段特征 | 平台重心 | 北极星指标 |
|---|---|---|---|
| **L1 工具增强期** | IDE 插件/问答/补全，点状提效，流程不变 | 统一接入与权限、采纳运营、安全合规基线 | 周活跃渗透率、代码采纳率 |
| **L2 流程融合期** | 评审/测试/流水线等环节级 Agent 上岗并融入流程 | 平台能力 MCP 化、上下文与知识供给、环节打通、门禁适配 | 环节周期缩短、AI 缺陷发现占比 |
| **L3 编排代理期** | 中循环成型：人委派 + 验收，Spec 驱动、异步后台 Agent | Agent 注册中心、编排与委派协议、证据链 PR、人机协作界面 | 委派任务占比、验收一次通过率 |
| **L4 自治治理期** | 风险分级自治，组织级多人多 Agent 协作 | 控制平面（身份/策略/审计）、Token FinOps、评测体系、度量演进飞轮 | 端到端交付周期、单位成本交付价值 |

当前行业水位处于 L2→L3 的过渡带：信通院口径下 L3 企业占比 29.75%[^117^]，腾讯、字节等头部组织已在局部业务进入 L3（50% 新增代码由 AI 生成、评审 AI 参与度 94%[^70^]），但即便是它们，L4 所需的控制平面与治理体系也仍在建设中。对多数大型组织而言，**2026—2027 年的现实目标是把 L2 做厚、把 L3 跑通，而不是直接追逐 L4 叙事**。

### 5.4 辅助轴三：度量（北极星 + 护栏）

AI 原生演进的度量体系必须同时回答"有没有更快"和"有没有更稳/更省"，否则就会被"AI 生产力悖论"误导[^33^]。建议采用"北极星 + 护栏"的双层结构，并对接业界已验证的框架：DX Core 4 的四个维度（速度、有效性、质量、影响）[^34^]，DORA 2025 的七项 AI 放大能力（明确 AI 立场、健康数据生态、AI 可访问的内部数据、版本控制、小批量工作、用户中心、高质量内部平台）[^39^]，以及信通院正在制定的智能研发效能度量标准[^117^]。

| 层 | 指标 | 说明 |
|---|---|---|
| 北极星（L2→L3） | 变更前置时间（需求→上线） | 大循环综合速度，唯一端到端指标 |
| 北极星（L3+） | 委派任务占比 × 验收一次通过率 | 中循环健康度的乘积指标，防止"委派多、返工多" |
| 护栏·质量 | 变更失败率、逃逸缺陷率、代码 churn 率 | 防止吞吐假象：churn 从 3.1%→5.7% 是典型警示[^33^] |
| 护栏·消化 | 人均评审负荷、评审覆盖率、PR 从创建到合并时长 | 监控瓶颈下移，评审覆盖率腰斩是 2x 强制令的教训[^79^] |
| 护栏·成本 | 单位合并 PR 的 Token 成本、AI 成本/人力成本比 | 应对 2028 年 AI 编码成本超薪酬的预测[^114^] |
| 护栏·体验 | 开发者满意度、DXI 指数 | DX 数据显示 AI 可提升感知效率但不一定提升满意度[^34^] |

落地这套度量时有三个操作要点。第一，**先建基线再上手段**：在引入任何 Agent 能力之前，用 4—6 周时间采齐北极星与护栏指标的基线，否则后续的"提效"永远说不清——Booking.com 的 16% 提升之所以可信，正因为它是统一度量框架下的对照结果[^35^]。第二，**警惕指标博弈（Goodhart 定律）**：PR 数量、代码行数、AI 代码占比这类供给侧指标极易被"刷量"，腾讯"新增代码 50% 由 AI 生成"这类数据应作为渗透度参考而非效能证据[^70^]，效能证据必须落在端到端周期与质量护栏的联合改善上。第三，**指标随成熟度换挡**：L1 看渗透、L2 看环节周期、L3 看委派与验收、L4 看端到端与单位经济，用 L1 的指标考核 L3 的工作（或反之）都会误导投入方向。

### 5.5 如何用框架定位问题与排定优先级

框架的使用方式是"矩阵定位、三轴定策"。以一个典型问题为例——"AI 生成的代码质量不稳定"：先在矩阵中定位到"代码评审 × 人—Agent 结对"与"开发测试 × 人—Agent 结对"两格；再用循环轴判断它是小循环问题（测试不足以作为验收信号）还是中循环问题（验收证据链缺失）；然后用成熟度轴确认组织当前级别能否支撑对应解法（L2 阶段应优先补测试与上下文，而非上评审 Agent）；最后用度量轴选定验证指标（churn 率、逃逸缺陷率）。这个过程把一个模糊的情绪性判断，转化为可在两周内立项的平台工作项。

排优先级时建议遵循三条原则。**瓶颈优先**：优先解决矩阵中"压力值高且位于传导链上游"的格子（上下文工程、测试信号、评审消化），因为下游环节的提速会被上游瓶颈吞噬[^145^]。**证据优先**：凡是能同时产出"过程证据"的工作（证据链 PR、Agent 行为追踪）优先于纯体验优化，因为治理与度量都建立在证据之上。**可逆性定价**：对不可逆风险高的环节（生产变更、数据操作）保持人审闸门，把自治额度优先投向可逆性高的环节（文档、测试补充、依赖升级）——Spotify 正是用后台编码 Agent（Honk）批量处理依赖升级与迁移这类可逆任务，累计合并 1500+ 个 AI 生成 PR、相对手工节省 60—90% 工时[^168^]。

## 六、行业实践对标

把上述框架投向行业，可以清晰地看到不同组织在矩阵不同象限的落子。国际厂商中，**GitHub** 的主线在"开发实现 × 人—Agent 结对/编排"：云端编码 Agent 承接 Issue、异步产出草稿 PR[^68^]，自定义 Agent 机制（.github/agents）实质上是一个轻量 Agent 注册中心[^77^]，同时开源 Spec Kit 推动需求侧的规约驱动开发[^45^]。**Anthropic** 的主线在人—Agent 协作协议本身：Claude Code 的权限模式梯度、93% 批准率揭示的审批疲劳、以及"用更少决策点替代更多确认框"的安全设计[^148^]，加上对真实自治行为的持续测量[^143^]。**Spotify** 的后台编码 Agent（Honk）建立在 2022 年就开始运营的 Fleet Management 平台与 Backstage 门户之上——先做到"每个组件有属主、构建标准化、测试完备、LLM 作为评审裁判"，才让 Agent 在沙箱中批量执行迁移类任务，累计 1500+ PR、节省 60—90% 工时，其工程团队的总结"你无法安全地自动化你不理解的东西"正是平台先行论的最佳注脚[^168^]；**Booking.com** 则以 16% 的可测量提升证明了统一度量（DX Core 4）对兑现 AI 价值的作用[^35^]。

国内组织的实践与信通院 AI4SE 标准体系（已发布代码大模型、智能开发、智能测试三项评估，效能度量、智能运维、智能体标准制定中）[^117^]形成了呼应。**腾讯**是 L3 特征最完整的样本：CodeBuddy 覆盖 90%+ 工程师、50% 新增代码由 AI 生成、研发效能提升 20%+、编码时间缩短 40%、微信支付交付周期缩短 31%，WeDev 研效平台与 AnyDev 环境供给构成底座[^70^][^66^]；其企业级落地（如某保险集团提效 18%）也验证了对外输出能力[^74^]。**字节跳动**以 TRAE 为核心推进"AI 原生 IDE"，内部渗透率 92%+，并开始在企业版中内置效能追踪[^55^][^43^]，火山引擎提出的"Agent 优先的软件研发"主张把 TRAE 定位为"The Real AI Engineer"[^58^]。**阿里**的路径是平台能力 MCP 化：云效 MCP Server 让 Agent 贯通需求—编码—MR—流水线全链路[^61^]，通义灵码在企业客户中达到 37% 的 AI 代码占比[^74^]，哈啰的采纳率超过 20%[^83^]。**工商银行**代表了金融级的稳健路线：27 项智能研发能力、自动代码缺陷检出率超 40%、单位时间有效代码量提升 22.9%，并明确向"AI 主导智能研发"演进[^116^]。**中国联通**的 ChatCode 则以 AI 生成代码占比 19% 起步，展示了央企从 L2 做起的典型路径[^126^]。

| 组织 | 关键数据（自报口径） | 矩阵中的主要落点 |
|---|---|---|
| GitHub | 云端 Agent GA，自定义 Agent 机制 | 开发实现 × 结对/编排；需求规格（Spec Kit）[^45^][^68^] |

## 七、演进路线建议（大型组织成熟研效平台）

针对"已有成熟研效平台、千人以上研发规模"的组织，建议按三个 Horizon 规划 18—24 个月的演进，每个 Horizon 都能在矩阵上找到明确的格子，且前一阶段为后一阶段提供不可替代的地基。

**Horizon 1（0—6 个月）：把 L2 做厚——上下文、验证、MCP 化。** 重点工作四项：其一，全组织仓库 AGENTS.md 覆盖工程（模板 + lint + 评测），这是投入产出比最高的单项[^128^]；其二，验证环境按需供给（对标 AnyDev 的"1 天→1 分钟"[^70^]），让测试成为 Agent 可用的验收信号；其三，平台核心能力（需求、代码、流水线、环境）MCP 化发布，先只读、后写操作[^61^]；其四，度量基线重建——把 churn 率、评审负荷、评审覆盖率纳入护栏指标，防止吞吐假象[^33^]。这一阶段的成功标准是：Agent 能"自助"完成边界清晰的任务且质量可验。

**Horizon 2（6—15 个月）：把 L3 跑通——中循环工业化。** 重点工作四项：其一，证据链 PR 标准（每个 Agent 产出必须携带：变更摘要、验证证据、影响面分析、回滚方案），把人的验收从"逐行读代码"升级为"审证据"[^87^]；其二，Agent 注册中心与委派协议（任务模板、风险定级、验收人指派），把委派从个人技巧变成平台能力[^93^]；其三，评审体系重构——机器预检 + 评审 Agent 初筛 + 人聚焦架构与业务逻辑，明确"自动化评审超过人工"后的质量门禁新标准[^79^]；其四，高价值场景的多 Agent 编排试点（需求→多仓库变更、测试补全批处理）。成功标准是：委派任务占比与验收一次通过率双升，评审负荷下降。

**Horizon 3（15—24 个月）：为 L4 奠基——控制平面与组织治理。** 重点工作四项：其一，Agent 身份、权限、审计的统一控制平面（对标 Agent 365 把 Agent 纳入员工式治理[^96^]）；其二，风险分级自治模型（可逆性 × 影响面矩阵）与 HITL→HOTL→自治的晋升机制（95% 批准率、<1% 错误率、30 天稳定期等量化门槛[^80^]）；其三，Token FinOps——单位合并 PR 的 AI 成本进入工程例会，避免"AI 账单超过薪酬账单"的失控[^114^]；其四，组织侧配套：工程师能力模型改版（规格工程、编排、质量判断[^103^]）、代码所有权与问责制度更新、以及新人培养路径设计。成功标准是：低风险变更的全自动交付占比稳定上升，高危变更的人审强度不降反升。

## 八、组织与角色变化

平台演进最终会传导到组织与人的层面，这一部分往往是技术规划中最容易被低估的。角色层面的主轴是"从实现者到编排者与验收者"：Gartner 预测 2028 年 90% 的企业工程师使用 AI 助手、角色转向编排[^102^]；Cursor 数据研究亦显示，在 Agent 默认开启的公司中 PR 合并量提升 39%，资深工程师的时间从敲代码转向规划与监督[^142^]。Thoughtworks 提出的"expert generalist（专家型通才）"概念值得写进能力模型——当 Agent 可以补齐具体技能，人的价值集中到问题定义、系统思维与质量判断上[^103^]，对应的五项新技能是：规格工程、系统设计、Agent 编排、质量判断与上下文工程[^103^]。

组织层面有三道必答题。**一是团队 sizing 逻辑的变化**：tiny teams 的可行性依赖平台把非编码工作（环境、权限、流程合规）进一步自动化，否则小团队会被运维性事务拖垮[^13^]。**二是责任与问责的重新立法**：当自动化评审超过人工评审[^79^]、Agent 产出占代码一半[^70^]，"谁合并谁负责"需要细化为"人审人负责、机审平台担责边界、Agent 行为全程可审计"的三层结构。**三是人才梯队的断层风险**：初级任务被 Agent 吸收后，需要主动设计"人机协作下的新手成长路径"（如以验收、测试设计、故障复盘为入门任务），否则五年后组织会发现无人能做 L4 所需的"高风险人审"。这些问题的答案无法从工具采购中获得，它们是平台团队、技术管理者与 HRBP 的共同议程。

## 结语：三个转变

回到最初的问题——AI 原生探索中，领域划分和大小循环发生了什么改变？可以浓缩为三个转变。**从环节到循环**：流程阶段的边界没有消失，但分析单位应从"环节"升级为"循环"——小循环内卷、中循环新生、大循环瘦身升格，瓶颈整体从生产速度下移到验证与消化能力[^145^][^79^]。**从工具到协作再到治理**：协作问题完成了三级跳，人—Agent 的信任校准、人—多 Agent 的编排协议、多人—多 Agent 的责任治理，各自对应不同的平台工位，且必须按序推进[^135^][^80^]。**从平台到控制平面**：研效平台的服务对象从人扩展为人与 Agent，平台定位从 IDP 升级为混合劳动力的控制平面，AX 与 DX 并重[^6^][^90^]。

对演进规划而言，一张"流程阶段 × 协作层次"的矩阵负责定位问题，循环、成熟度、度量三条轴负责定策与验证；而贯穿始终的原则只有一条：**先把验证与验收做成平台能力，再放手让 Agent 跑得更快**——因为在这个时代，消化能力才是真正的产能。
