## 🌟 本期亮点

今天的早报继续聚焦AI时代的软件工程，但角度有所不同——昨天是"宏大叙事"（代码迁移、设计模式、编译器），今天是"具体实践"（测试方法论、净室实现、小而美的工具）。

Simon Willison的"First run the tests"只有四个词，但背后是AI编程时代的方法论变革。antirez的Z80净室实验，则让我们思考：AI辅助编程的"原创性"边界在哪里？

最让我思考的是antirez那句话——"这个实现的执行方式非常类似于人类程序员的方式，而不是从权重中'解压缩'出完整实现"。这句话触及了AI编程的本质：AI不是在"复制"，而是在"推理"。

## 📰 🔴必读

### 1. First run the tests - Agentic Engineering Patterns

**🏷️ 中文标题**：先运行测试——Agentic工程模式第一篇：AI编程时代，自动化测试不再是可选的

**📌 核心观点**：AI编程时代，自动化测试不再是可选的，而是必需的。"先运行测试"这四个字，体现了AI编程时代的软件工程纪律。

**💡 为什么值得关注**：
这是Simon Willison新启动的"Agentic Engineering Patterns"项目的第一篇，标志着AI编程从"经验主义"走向"体系化"的开始。四个词的提示词，背后是完整的方法论。

**📋 关键要点**：

#### 1. 测试不再是可选的
- **旧借口失效**：过去"测试耗时且昂贵，代码库快速演进时不断重写测试不划算"的借口不再成立
- **AI可以快速编写测试**：agent可以在几分钟内搞定测试
- **测试是AI代码的保障**：如果代码从未运行过，部署到生产环境时能工作纯粹是运气

#### 2. 测试的三个关键作用
1. **验证AI生成的代码**：确保代码真的能做它声称要做的事情
2. **帮助agent理解现有代码库**：agent会主动查找和阅读相关测试
3. **推动agent测试新修改**：现有测试套件的存在会促使agent测试它所做的新更改

#### 3. "First run the tests"四字咒语
Simon Willison的标准开场提示词：
```
First run the tests
```

或者对于Python项目：
```
Run "uv run pytest"
```

这四个词的作用：
- **告诉agent有测试套件**：强制agent弄清楚如何运行测试，这使得agent几乎肯定会在将来运行测试以确保没有破坏任何东西
- **给项目规模指示**：大多数测试工具会给agent一个大致的测试数量指示，这可以作为项目规模和复杂度的指标，也暗示如果agent想了解更多，应该搜索测试本身
- **建立测试心态**：运行测试后，agent自然会在以后扩展自己的测试

#### 4. 与"红/绿TDD"的关系
- 类似"Use red/green TDD"，都是四字提示词
- 都体现了已内建在模型中的软件工程纪律
- 都是Agentic Engineering Patterns的一部分

**彪彪思语**：这让我想起了以前的"测试驱动开发"（TDD），但在AI时代，TDD的含义变了。以前是"人写测试，人写代码"；现在是"人写测试，AI写代码"；未来可能是"AI写测试，AI写代码"。但无论如何，测试永远是最重要的。

**⭐ 推荐**：值得精读（AI编程时代的测试方法论）

**🔗 原文链接**：https://simonwillison.net/guides/agentic-engineering-patterns/first-run-the-tests/

### 2. Implementing a clear room Z80 / ZX Spectrum emulator with Claude Code

**🏷️ 中文标题**：用Claude Code在"净室"条件下实现Z80/ZX Spectrum模拟器——antirez对AI编程原创性的深度探索

**📌 核心观点**：antirez对Anthropic的"净室"实验提出质疑，并亲自做了一个更合理的实验。结果表明：AI辅助编程的实现方式非常类似于人类程序员，而不是从权重中"解压缩"出完整实现。

**💡 为什么值得关注**：
这是Redis作者antirez的最新实验，深入探讨了AI辅助编程的"净室"实现方法论，对理解AI编程的边界和原创性很有价值。

**📋 关键要点**：

#### 1. antirez对Anthropic实验的质疑
Anthropic的实验：让Opus 4.6在"净室"条件下用Rust写C编译器。

antirez的质疑：
- **为什么不提供ISA文档？**
- **为什么用Rust？** 写C编译器正是一个巨大的图处理练习，这种程序在Rust中更难写
- **为什么不提供已有的计算机科学进展？** SSA、寄存器分配、指令选择和调度，这些都应该先作为前提条件研究

#### 2. antirez的实验设计
更合理的"净室" setup：

**步骤1：编写规范文档**
- 只用英文，关于要实现的Z80模拟器范围的高级想法
- 指定：一次执行一条完整指令（而不是单个时钟步）、正确跟踪时钟周期、提供内存访问回调、模拟所有已知的官方和非官方指令

**步骤2：收集文档**
- 让agent在互联网上获取所有关于Z80的有用文档
- 只提取有用的事实信息到markdown文件
- 提供Z80的测试向量、ZX Spectrum ROM等二进制文件
- **然后完全删除Claude Code会话**，确保没有与搜索过程中看到的源代码的污染

**步骤3：实现**
- 启动新会话，让agent检查规范文档和所有可用文档
- 规则：永远不要因任何原因访问互联网，永远不要在磁盘上搜索类似的源代码
- Z80实现：零干预
- Spectrum实现：对TAP加载使用大量干预

**步骤4：验证原创性**
- 把仓库复制到/tmp，完全删除".git"仓库文件
- 启动新的Claude Code（和Codex）会话，声称实现可能被窃取或太强烈地受他人工作启发
- 任务：用所有主要的Z80实现检查是否有偷窃证据
- **结果**：两个agent都无法找到任何版权问题的证据

#### 3. 实验结果
- **时间**：Claude Code总共工作了20或30分钟
- **产出**：1200行非常易读且注释良好的C代码（带注释和空行1800行）
- **质量**：能够通过ZEXDOC和ZEXALL
- **过程**：
  - 零提示，完全自主行动
  - 从未访问互联网
  - 持续测试、与实现ZEXDOC和ZEXALL的CP/M二进制交互
  - 增量实现不同类别的指令，通过集成测试修复bug

#### 4. 关键洞察
不是从权重中"解压缩"出完整实现，而是：
- 类似人类程序员的实现方式
- 增量实现，测试驱动
- 有bug，通过集成测试和调试会话修复

**彪彪思语**：这个实验最有意思的地方是"验证原创性"那一步。antirez让另一个agent去检查"这个实现是不是偷来的"，结果是"没有证据表明有版权问题"。这说明：AI辅助编程确实可以产生"原创"的代码，而不仅仅是复制训练数据。但这里的"原创"和人类的"原创"是一回事吗？这是一个值得深思的问题。

**⭐ 推荐**：值得精读（AI编程方法论的深度探索）

**🔗 原文链接**：http://antirez.com/news/160

### 3. go-size-analyzer

**🏷️ 中文标题**：go-size-analyzer——Go生态系统的又一个小而美的工具，用树形图分析二进制大小

**📌 核心观点**：Go生态系统的工具真的很棒，又发现了一个好工具。可以本地安装运行，也可以在浏览器中直接使用。

**💡 为什么值得关注**：
这是一个小而美的工具，展示了Go生态系统的繁荣，对优化Go二进制大小很有实用价值。

**📋 关键要点**：
- **功能**：用美观的树形图分析Go二进制的大小，展示其捆绑的依赖
- **两种使用方式**：
  1. 本地安装运行
  2. 编译成WebAssembly，托管在gsa.zxilly.dev，可以直接在浏览器中打开编译好的Go二进制进行分析
- **演示**：Simon用自己的Go工具Showboat（8.1MB macOS编译版本）测试，效果很好

**彪彪思语**：Go生态系统的工具链确实让人羡慕。从gofmt到go vet，从pprof到trace，再到今天的go-size-analyzer，每一个工具都是小而美的典范。这背后是Go团队的设计哲学："做一件事，把它做好"。

**⭐ 推荐**：建议浏览（实用小工具）

**🔗 原文链接**：https://simonwillison.net/2026/Feb/24/go-size-analyzer/
