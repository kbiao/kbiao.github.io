严谨性去了哪里？——当AI写代码时，工程质量如何保证

发表于 2026-02-25 更新于 2026-02-25 分类于 裁云记 阅读次数：
当AI开始写代码时，一个紧迫的问题浮现了：那些曾经体现在编写和审查代码中的工程严谨性，去了哪里？本文深度解读工程严谨性的五个新归宿：规范审查、测试套件、类型系统和约束、风险映射、持续理解。

“We kept asking the same question in every room: if AI handles the code, where does the engineering actually go? Nobody had the same answer. But everybody agreed the question is urgent.”

—— The Future of Software Engineering Retreat, February 2026

一个让人焦虑的问题

through works 最近组织一批专家做了一个关于软件工程未来的研讨，大家毫不怀疑 AI 会在不远的时间内接管大部分代码工作；大家都有一个隐隐的焦虑：AI写代码确实快，但是——质量怎么保证？

以前我们写代码，每一行都经过深思熟虑。代码审查时，我们会盯着每一行看：边界情况处理了吗？有没有性能问题？符合架构原则吗？

现在倒好，AI几分钟就能生成几百行代码。看起来很完美，参数验证、错误处理、数据库操作，一应俱全。目测很满意，合并到了主分支。

然后生产环境很快就报错了。

你是不是也有过这样的经历：AI写的代码，第一次看觉得”哇，这么完美”，上线后发现”AI怎么这么蠢？这么简单的边界情况都没处理？”

问题来了：当AI开始写代码时，那些曾经体现在编写和审查代码中的工程严谨性，去了哪里？

答案：严谨性没有消失，它只是迁移了

thought works 专家们推演当代码生产不再是问题，那么软件工程中曾经体现在编码和Code Review 中的工程规范并不会消失 ：工程严谨性没有消失，它只是换了个地方。

就像运维系统一样，以前我们是”出现故障 → 人工修复”，现在我们是”出现故障 → 分析根因 → 设计监控 → 自动告警”。

与AI协作也是一样。不要只修复症状，要解决根本原因。

工程严谨性从代码本身向上游和下游迁移，找到了五个新的归宿。

严谨性迁移的五个目的地

1. 上游到规范审查

核心洞察：如果AI从规范生成代码，那么规范现在就是捕获错误的最高杠杆工件。糟糕的规范会大规模产生糟糕的代码。

这是一个深刻的范式转变。

以前我们的工作流程是：

  1. 产品经理写一个模糊的用户故事：”作为一个用户，我想登录系统”
  2. 开发者把它翻译成代码，中间要补全无数细节
  3. 代码审查发现问题，反复修改
  4. 终于上线了

现在这个流程变成了：

  1. 写一个精确的规范（这是新的关键步骤）
  2. AI从规范生成代码
  3. 测试验证代码是否符合规范

传统的用户故事太模糊了。”作为一个用户，我想登录系统”——这样的描述对于AI来说太不精确了。

一些团队正在采用结构化方法，如 EARS（Easy Approach to Requirements Syntax）、状态机和决策表。这些不是新技术，但它们被重新发现，因为它们为AI Agent提供了足够的精度来产生正确的实现。

当然更流行的概念是 做 spec 驱动开发，把严谨的描述转移向需求拆解的文字中，要求文字尽可能有如同代码般的编译执行正交逻辑。这种场景是已经在发生，不少团队推动 sdd 流程，但是写代码转成写文字会让这个工作更高效更有价值吗？

2. 进入测试流程成为一等公民

核心洞察：测试驱动开发（TDD）从AI编码Agent中产生了显著更好的结果。TDD防止了Agent编写验证错误行为的测试的失败模式。

“I’ve gotten better results from TDD and agent coding than I’ve ever gotten anywhere else, because it stops a particular mental error where the agent writes a test that verifies the broken behavior.”

TDD不是新技术，它已经存在了二十年。但在AI时代，它被重新定义为一种提示工程形式。

关键观点：

  • TDD被重新定义为一种提示工程形式
  • 测试成为非确定性生成的确定性验证
  • 一些从业者将审查工作完全转移到测试套件，将生成的代码视为可消耗的
  • 如果测试正确且代码通过测试，无论代码看起来如何，代码都是可接受的

这正好对应我之前关注的 Harness工程——任何时候你发现Agent犯错，你都要花时间设计一个解决方案，使Agent永远不会再犯那个错误。

最近有不少博客提到这类重构或者实验，这确实是值得深入的方向，因为 AI 写代码确实快了，TDD 额外的工作仍然是代码，那么以前写测试代码本身的复杂度和可行性也变高了，具体的执行落地方式还有待探讨。

3. 进入类型系统和约束

核心洞察：与其在生成后审查代码，从业者正在探索如何使错误的代码无法表示。这借鉴了形式化方法和强类型系统的思想，不是作为学术练习，而是作为Agent输出的实用护栏。

这里有一个重要的区分：

  • 规范：描述应该改变什么
  • 约束：定义允许更改的有界上下文，包括必须不接触的内容

约束的价值：

  • 限制爆炸半径
  • 让Agent安全地跨域边界工作
  • 当必须打破约束时，它标志着新的系统边界并提示重构

这种我的理解是仍然在技术探讨阶段，类似云原生编程的语言（go，rust），也许会有 Agent Native 的编程范式出现。目前的约束是体现在 agent 的提示词中的概率性保护，而没有落地到语言和执行层面的安全。

4. 进入风险映射

核心洞察：不是所有代码都承担相同的风险。按业务爆炸半径对代码进行分层，区分内部工具、面向外部的服务和安全关键系统。

“Instead of asking ‘did someone review this code?’ organizations need to ask ‘what is the blast radius if this code is wrong, and is our verification proportional to that risk?’”

范式转变：

  • 从工艺模型（每一行都是手工审查）→ 风险管理模型（验证投资与曝光度匹配）

内部系统， B 端业务的中后台管理系统确实是在当前 AI 浪潮下最快实践大模型提效的业务选择。这些业务传统上对于质量和发布流程的管控就较弱，更快的处理比更严谨的修复更重要。

5. 进入持续理解

核心洞察：如果代码变化的速度超过了人类可以审查的速度，那么通过代码审查构建心智模型的传统模式就会崩溃。

替代方案：

  • 每周架构回顾
  • 多人同时在同一代码上工作的结对编程
  • AI辅助的代码理解工具，按需生成系统概述

深层担忧：

  • 代码审查历史上既是学习机制，也是质量门
  • 指导、共享理解和代码库熟悉度都是通过审查发生的
  • 失去这个渠道而不替换它会造成随着时间推移而累积的理解差距

“Paired programming solves all of this. If it’s important to understand the system, then do it all the time. You don’t do it in little phases where you have your code review. Constantly trying to understand what this code is doing.”

就像 DevOps 的思想推动 CI CD 的实施 ， 如果人对业务系统始终需要深入的理解和掌控，那么业务和架构的理解就不能只发生在评审阶段，需要在所有的环节建立对系统的合适抽象层级的理解和反馈。

这不是关于信任，而是关于验证

这些变化的核心是一个深刻的认识：在AI时代，工程严谨性不再体现在对代码的信任上，而是体现在对验证的投资上。

我们不再问：”这个人写的代码可信吗？”

我们开始问：

  • “这个规范足够精确吗？”
  • “这个测试套件足够全面吗？”
  • “这些约束足够严格吗？”
  • “这个风险评估准确吗？”
  • “我们对系统的理解足够深入吗？”

工程严谨性不再体现在个人的技艺中，而是体现在系统的设计中。公司业务中我们也倾向于用系统设计，制度设计，流程设计去化解风险，追求确定性，而不是依赖一两个英雄人物救火。只是随着 AI 的进展，这样的要求已经深入每个一线工程师，而不是特定团队，领导，组织的职责。

“The retreat didn’t produce a roadmap. It produced a shared understanding that the map is being redrawn and that the people best positioned to draw it are the ones willing to admit how much they don’t yet know.”

工程严谨性没有消失。它只是换了个地方。

它从代码本身，迁移到了规范、测试、约束、风险映射和持续理解中。

这不是一个关于”失去”的故事。这是一个关于”重新发现”的故事。那些我们以为已经过时的，或者仅存在于教科书的理想技术（TDD、形式化方法、结构化规范），在AI时代突然变得重要且可行。

而那些我们以为是核心的技能（编写特定语法的代码），可能变得不那么重要了。

但有一样东西永远不会变：对本质的追求，对系统的思考，对质量的坚持。

这些才是工程严谨性的真正灵魂。无论代码是谁写的，这些灵魂永远不会过时。

当AI开始写代码时，我们终于可以停止纠结于代码的表面，开始专注于工程的本质了。从”编写代码”转向”设计系统”，开发规范设计、测试设计、约束设计的技能，不是中高阶工程师的要求，是对每个工程师的基本要求。
