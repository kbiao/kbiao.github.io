从 Prompt 工程到 Skills：LLM 上下文管理的工程演进

发表于 2026-02-15 更新于 2026-02-22 分类于 技术人生 阅读次数：

由小龙 🐉 协助整理创作

核心观点：不同概念的演进本质是在有限上下文窗口内引导模型更好输出的工程手段的深化

现在做LLM相关的开发，你肯定听过Prompt工程、上下文工程、RAG、Skills、Agent这些概念。一开始我也觉得这些概念挺玄乎的，一会儿一个新名词，感觉像是在造轮子。但深入了解后发现，这其实是一条清晰的工程演进线——本质都是在解决同一个问题：如何在有限的上下文窗口里，让模型输出最好的结果。

第一阶段：Prompt 工程时代——把单次请求做好

刚接触LLM的时候，大家都是从Prompt工程开始的。什么是Prompt工程？说白了就是琢磨怎么给模型写提示词，让它输出你想要的结果。

经典的Prompt工程技巧就那几样：

  • Few-shot（少样本学习）：给模型几个示例，它就知道该怎么输出了
  • CoT（思维链）：让模型一步步思考，而不是直接给答案
  • 角色设定：告诉模型“你是一位资深工程师”，它就会更专业
  • 输出格式约束：明确告诉它用JSON还是Markdown，避免输出乱七八糟的格式

但Prompt工程有个很大的问题：每次都得从零开始，模型没有“记忆”。你这次给它的提示词，下次对话它就全忘了。

第二阶段：上下文工程时代——让模型“看到”相关信息

后来大家发现，光优化单次请求不够，还得让模型“看到”更多相关信息。于是就有了上下文工程的概念。

核心洞察是：Prompt不只是“输入”，而是动态构建的上下文。你不能把所有信息都塞给模型，因为上下文窗口是有限的，你得挑最相关的放进去。

这个阶段最火的就是RAG（检索增强生成）：

  • 先把你的知识库存起来（比如你的文档、笔记）
  • 用户问问题时，先从知识库检索最相关的几篇
  • 把检索到的内容和用户的问题一起塞给模型

除了RAG，还有系统提示词和用户提示词的分离，多轮对话的状态管理（比如保留最近的对话，摘要更早的内容）。

第三阶段：Skills / Agent 时代——可组合的能力单元

再往后，大家发现只有动态上下文还不够，复杂任务需要复用能力。于是就有了Skills（技能）的概念。

什么是Skill？Skill是封装了工具调用 + 上下文模板 + 执行逻辑的单元。从Function Calling到Tools再到Skills，这是一条清晰的演进线。

Skill的核心价值是：

  • 模块化：把常用的能力封装起来，不用每次都重写Prompt
  • 可组合：多个Skill可以组合起来完成复杂任务
  • 可维护：修改一个Skill，不用改所有用到它的地方

本质思考：我们到底在解决什么问题？

回头看这条演进线，你会发现所有概念都在解决同一个约束：上下文窗口是有限的。

阶段核心特征解决的问题关键提升
Prompt 工程单次输入优化如何让单次请求效果更好提示技巧
上下文工程动态上下文构建如何让模型”看到”相关信息信息检索与注入
Skills可组合的能力单元如何让复杂任务可维护、可复用模块化与编排

共同本质都是：选择什么信息放入窗口，以什么形式组织。

工程启示

对我自己来说，这条演进线带来了三个启示：

  1. 不要神化任何一个概念：理解它解决的问题，选择适合你场景的粒度就好——简单任务用Prompt，需要知识用RAG，复杂流程用Skills
  2. 选择适合你的粒度：别什么都想用最“高级”的概念，杀鸡用牛刀只会增加复杂度
  3. 未来方向：自动化的上下文优化（Auto-Prompting, Context Compression）肯定是趋势，但现阶段还是得靠我们自己来设计

不知道你在实际项目中用到哪个阶段的技术最多？你觉得Skills概念会被什么取代？还有，上下文窗口越来越大（100K → 1M → ∞），这些技术还有意义吗？
